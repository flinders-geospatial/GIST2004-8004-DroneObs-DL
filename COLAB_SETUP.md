# Instructor setup for the drone observation Colab

There are two student notebooks, each generated by a builder script. Edit
the builder and regenerate rather than touching the notebook JSON.

| Notebook | Builder | Week |
|---|---|---|
| `drone_observation_yolo_colab.ipynb` | `build_colab_notebook.py` | train, track and count on the teaching clip |
| `drone_observation_field_footage_colab.ipynb` | `build_field_notebook.py` | count vehicles in the class footage |

Most of this file is about the first notebook. The second is covered under
"Second notebook" near the end.

## Course files

These four files need to sit somewhere public where `<base URL>/<file name>`
resolves for each one. The notebook's link field is pre-filled with the
current bucket URL; if the bucket changes, update `COURSE_DATA_URL` in the

## Models

The notebook sticks to plain names: the student's run is `my model`,
`reference_model.pt` is `backup model` and `strong_vehicle_model.pt` is
`bigger model`. Every dropdown defaults to `my model`.

The backup is YOLO11n trained 50 epochs at 1024 px on this dataset: mAP50
0.449, mAP50-95 0.245 on the pilot test set. Student runs start from
`yolo26n.pt`.

The bigger model is the YOLO11s at 960 px from the old multi-source
pipeline: mAP50 0.852 on its own test set, which used a two-class
vehicle/person scheme. The two mAP figures come from different test sets and
label schemes so they aren't comparable. The notebook only uses its
`vehicle` class. The 327 MB YOLO11x checkpoint stays local.

## Training settings

`epochs` 20, `imgsz` 960, `batch` 12. Batch 8 peaked around 7 GB on the
Colab T4. A local run at batch 16 peaked at 13.7 GB reserved, too close to
the T4's 15 GB for class use, so the notebook uses 12. If a run still hits
out-of-memory, drop back to 8.

Training runs on `/content` and copies `best.pt` and the plots to Drive when
it finishes. Don't train against files mounted from Drive. Colab's free GPU
type and availability vary, so don't promise a completion time.

## Class sequence

1. Run setup and the fetch cell, watch the embedded clip, then run
   extraction, the dataset audit, and the label examples.
2. Run the stock pretrained model on the default test photo; students can
   paste any image address and rerun. Then cover transfer learning and the
   training settings.
3. Tick `TRAIN_MODEL` and train.
4. If a runtime is interrupted, the note at the top of section 5 covers the
   switch to the backup model.
5. Compare the student's model and the bigger model, stacked on the same
   frame with a parameter table.
6. Draw one or more lines in PolygonZone, paste its NumPy output over
   `LINES`, and run the tracking and counting cells. The CSV has a `line`
   column.
7. Download the annotated video and compare the CSV with a manual count.

Line counts assume a stationary or stabilised camera. If the camera pans or
drifts the line won't sit over the same stretch of road; the notebook warns
students about this.

## Second notebook: the class footage

`drone_observation_field_footage_colab.ipynb` is the short follow-up for the
week after the flight. There is no training. Students connect Drive, load the
`best.pt` their first run saved
(`MyDrive/GIST2004-8004/my-droneobs-results/droneobs_yolo26n/best.pt`) or
choose the backup or bigger model, paste a class clip link, draw lines in
PolygonZone, and run the same detect, track and count loop. Outputs go to the
same Drive folder as before.

The notebook fetches `reference_model.pt` and `strong_vehicle_model.pt` from
the course link, so the bucket has to stay up for this lab as well. The clip
field opens with the teaching clip, which is how I rehearse before the class
clips exist. `CONFIDENCE` defaults to 0.5 in this notebook; the audit
questions send students to 0.25 and 0.75 to see the trade-off.

The 2026 clips, in the bucket beside the other files:

| File | Length | Size | Scene |
|---|---|---:|---|
| `intersection_a_mini4.mp4` | 3:00 | 91 MB | Mini 4, steep view of a signalised intersection with roadworks on one corner |
| `intersection_b_low_mini5.mp4` | 1:45 | 32 MB | Mini 5, low view across a large intersection beside a noise wall |
| `intersection_b_high_mini5.mp4` | 3:00 | 51 MB | Mini 5, the same intersection from higher up |

The Mini 5 files were also dropped from 60 to 30 fps. On the Mini 4 clip the
arm nearest the roadworks shows inbound approach lanes only, so a line there
counts one direction.

### Preparing the class clips

Trim each DJI file to the steady hover, drop the audio, and bring it down to
the 1280 width the notebook processes at. One command per clip, with the
start time and duration adjusted to the footage:

    ffmpeg -i DJI_0031.MP4 -ss 0:20 -t 3:00 -vf scale=1280:-2 \
      -c:v libx264 -crf 22 -pix_fmt yuv420p -an -movflags +faststart \
      intersection_a.mp4

Keep each clip to two or three minutes. Upload them to the course bucket
beside the other files and hand out the full links (`<base URL>/<file name>`).
Plain file names, no spaces.

The raw 4K files also work if there is no time to transcode. I checked the
notebook locally (2026-09-08) against 30-second 4K clips in H.264, HEVC,
10-bit HEVC and 60 fps HEVC, which covers the Mini's recording modes: every
one downloaded, probed, seeked for the late frame, and counted. Transcoding
is still the better option for three reasons. The clip player in the
notebook streams the file straight from the bucket, and browsers without
hardware HEVC support play nothing. A raw file is around 2 GB for three
minutes, against roughly 70 MB transcoded, so forty students downloading at
once is slower and costs egress. And Colab's two CPU cores decode 4K far
slower than the teaching clip; 10-bit HEVC was the slowest of the four here,
and 60 fps doubles the frame count, so a three-minute raw clip can take
several minutes in the counting cell. If a raw 60 fps file has to be used,
`FRAME_STRIDE = 2` halves the work.

### Class sequence

1. Run setup and the Drive cell. The cell lists which of the three models
   were found; students whose first run did not finish choose `backup model`.
2. Paste a clip link, watch the clip, and count one direction by hand.
3. Download `zone_reference.jpg`, draw lines in PolygonZone, paste the NumPy
   output over `LINES`. The preview draws the lines on the first frame and a
   frame near the end, so any hover drift shows up before counting.
4. Count 30 seconds to check the lines, then set `MAX_SECONDS` to 0 and
   rerun for the whole clip.
5. Audit the CSV against the hand count, then try `bigger model` from the
   model cell.

### Rehearsal checklist

- The notebook runs end to end on the teaching clip with `backup model`
  before any class clips exist.
- With a `best.pt` in the Drive path, `my model` is reported as found and
  loads.
- With no `best.pt`, choosing `my model` stops at the model cell with a
  message that names the path and says to choose another model.
- Each class clip link downloads, probes, and streams in the player.
- The first and near-last frame preview renders with the example line.
- `MAX_SECONDS = 0` on a full class clip finishes in a few minutes on a T4.
- The annotated MP4 and crossing CSV copy to Drive.

## PolygonZone

PolygonZone only picks the counting-line coordinates; it doesn't label
training data. If students label their own frames in a future version, split
by whole clip or time block, otherwise near-identical adjacent frames land
in both train and test and inflate the validation numbers.

- The public base URL resolves for all four file names.
- The teaching clip streams and plays after the fetch cell. The player

- The stacked comparison and its parameter table render.
- `zone_reference.jpg` downloads, PolygonZone's NumPy output pastes over

- The final annotated frame renders with cumulative counts, and the

## Version note

`supervision` 0.27 `LineZone.trigger` calls `np.cross` on 2-D vectors, which
NumPy 2 removed. Colab ships NumPy 1.x today so it works; if Colab moves to
NumPy 2, bump `supervision` and re-test the counting loop.
